# Staging environment as a full parallel stack

The deploy script (`deploy/deploy.sh`) takes `ENV=production|staging` and **defaults to staging**: a routine deploy can never hit production by accident; production requires the explicit `ENV=production` flag. A plain run stands up a complete, isolated staging environment — its own Lambda pair (`guito-api-staging`, `guito-api-authorizer-staging`), its own HTTP API with access logs, and its own secret (`guito-api/staging`), all tagged `Project=Guito` in eu-west-1 — reusing only the shared IAM role and the packaged code. Code is never shared between environments at runtime: sharing functions defeats the purpose of a deploy-test environment.

**Auth parity is a hard requirement.** Staging runs the full dual auth (Google ID token + agent API key) with the SAME `GOOGLE_CLIENT_ID`/`GOOGLE_ALLOWED_EMAILS` as production, read at deploy time from the prod authorizer's function configuration and enforced — a staging run fails hard rather than deploying the human path deny-closed silently, and the appsettings layer (`appsettings.Staging.json`, `ASPNETCORE_ENVIRONMENT=Staging`) keeps validation fully on. A staging env with relaxed auth tests a different auth surface than prod and is a blind spot. Staging gets its OWN agent key, generated on first deploy inside `guito-api/staging` (fresh key + the dev/staging service-account key in one `SecretsPayload`); the prod key against staging returns 403, which is itself an integration assertion.

**Prod safety**: Lambda env updates merge into the current configuration (never replace), so redeploys never wipe policy set by a previous run; the shared role's secret-read policy is pinned to explicit `guito-api/prod-*` and `guito-api/staging-*` secret ARNs, so neither environment can read the other's secret and a staging run cannot break prod's secret access. Staging deploys must be proven prod-safe by snapshotting prod function configuration before and diffing after — byte-identical is the acceptance bar.

**Considered Options**: sharing the prod functions/secret behind a staging flag (rejected — no isolation, staging traffic mutates prod state); per-env IAM roles (rejected as premature — one role with pinned per-env secret ARNs is sufficient at this scale).

**Consequences**: staging shares the dev/staging Google spreadsheet (the same sheet local dev targets); the SA key file is gitignored, so a first staging deploy on a new machine fails by design until that file exists. Integration tests (`tst/guito-api.IntegrationTests`) target this stack via its own agent key, and the prod-key-against-staging 403 is an assertion, not an accident.
