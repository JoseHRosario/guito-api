# Staging environment as a full parallel stack

The deploy script (`deploy/deploy.sh`) takes `ENV=production|staging` and **defaults to staging**: a routine deploy can never hit production by accident; production requires the explicit `ENV=production` flag. A plain run stands up a complete, isolated staging environment — its own Lambda pair (`guito-api-staging`, `guito-api-authorizer-staging`), its own HTTP API with access logs, and its own secret (`guito-api/staging`), all tagged `Project=Guito` in eu-west-1 — reusing only the shared IAM role and the packaged code. Code is never shared between environments at runtime: sharing functions defeats the purpose of a deploy-test environment.

**Auth parity is a hard requirement.** Staging runs the full dual auth (Google ID token + agent API key) with the SAME `GOOGLE_CLIENT_ID`/`GOOGLE_ALLOWED_EMAILS` as production, read at deploy time from the prod authorizer's function configuration and enforced — a staging run fails hard rather than deploying the human path deny-closed silently, and the appsettings layer (`appsettings.Staging.json`, `ASPNETCORE_ENVIRONMENT=Staging`) keeps validation fully on. A staging env with relaxed auth tests a different auth surface than prod and is a blind spot. Staging gets its OWN agent key, generated on first deploy inside `guito-api/staging` (fresh key + the dev/staging service-account key in one `SecretsPayload`); the prod key against staging returns 403, which is itself an integration assertion.

**Prod safety**: Lambda env updates merge into the current configuration (never replace), so redeploys never wipe policy set by a previous run. NOTE (reconciled Sep 2026): the original text claimed the role's secret-read policy was pinned to explicit `guito-api/prod-*` and `guito-api/staging-*` secret ARNs — that is not what was actually built. The shared role `MinervaAIAgent` carries the AWS-managed `SecretsManagerReadWrite` policy (full read/write on every secret in the account) and `IAMFullAccess`; `guito-api/human-auth` is readable for exactly that reason. Isolation therefore rests on deploy-time discipline, not IAM pinning. Tightening the policy to per-env secret ARNs (resource-scoped inline policy, adding `guito-api/human-auth` only where needed) remains an open hardening item. Staging deploys must be proven prod-safe by snapshotting prod function configuration before and diffing after — byte-identical is the acceptance bar.

**Considered Options**: sharing the prod functions/secret behind a staging flag (rejected — no isolation, staging traffic mutates prod state); per-env IAM roles (rejected as premature — one role with pinned per-env secret ARNs is sufficient at this scale).

**Consequences**: staging shares the dev/staging Google spreadsheet (the same sheet local dev targets); the SA key file is gitignored, so a first staging deploy on a new machine fails by design until that file exists. Integration tests (`sit/guito-api-auth.IntegrationTests` — auth contract — and `sit/guito-api.IntegrationTests` — business round-trip) target this stack via its own agent key, and the prod-key-against-staging 403 is an assertion, not an accident. The auth contract suite covers BOTH paths: the agent key path (staging key → 200) and the human Google ID token path — `scripts/run-deployed-tests.sh` mints a fresh ID token at run time via a refresh-token exchange against secret `guito-api/human-auth` (with `GOOGLE_CLIENT_ID` read from the prod authorizer's function configuration) and exports `GUITO_STAGING_GOOGLE_ID_TOKEN`; a failed exchange is fatal, because a run that silently tests only half the auth contract is the blind spot this ADR warns about.
