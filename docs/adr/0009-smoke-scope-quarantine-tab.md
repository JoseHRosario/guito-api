# Smoke scope: integration tests write to a quarantine tab, never to real tabs

The deployed-endpoint integration tests (staging on every push, production on master/dispatch) round-trip a €0.01 expense through the deployed API. Before this decision, that meant a permanent fake row — plus an empty "dummy row" leaked by list-latest's append-to-find-last-row trick — in the environment's real Expenses tab, i.e. in the sheet holding real financial data (dev/staging) and, on production deploys, in the prod sheet. We decided tests must **never write to a real tab, in any environment, ever**, and that the smoke still exercises the full write path in production (the point of a prod smoke is to verify the deployed wiring, which a staging-only write test cannot).

**The mechanism is a smoke scope, not a decoy run by the test.** The datastore target of the deployed API is server-side config (`ExpensesRange` etc.); an HTTP test client cannot redirect it. So the API gains a `X-Sheet-Scope: smoke` header: sheets-backed services resolve their ranges to smoke counterparts (`ExpensesSmokeRange`, `ExpensesLatestSmokeRange`, `ExpensesDateSmokeRange`) when it is present. Any authenticated caller may send it: it grants strictly less power than the agent key already does (writing the real tab), so there is no escalation to close. The only intended caller is the integration test suite. Each environment's spreadsheet gains a bare `Smoke Test` tab (anchor `B5`, no pre-existing layout or formulas); the scoped create still fills Year/Month on the rows it writes, exactly as it does on the real tab — the code path stays 1:1.

**Cleanup is a deterministic, id-scoped delete, and it is deliberately NOT a general delete-expense endpoint.** `POST /expense` now returns the Expense's opaque `id` in its response (always, for every caller). The integration suite captures it and calls `DELETE /Smoke/{id}`, which operates only on the smoke tab: it verifies the row behind the id still exists (read-before-delete), deletes the dimension, and returns 404 when the id is gone (idempotent on retry). A general `DELETE /Expense/{id}` was rejected — it would aim a destructive capability at real financial rows, reachable by any valid agent key; it returns to scope only when guito-ui needs delete/edit as a product feature. Inferring the target row ("last non-empty row") was also rejected: non-deterministic under crashed runs that leave residue.

**Prerequisite fix:** list-latest no longer mutates the datastore. The old implementation appended an empty row on every read (including `GET /Expense/match`, which reuses list-latest) to discover the last row index; it is replaced by a pure read of the date column. A read that writes is a bug in a financial app regardless of tests. **Expense ids are opaque** in the API contract — today the sheet row index, later a database key: the Sheets datastore is intended to become a presentation layer over a future Postgres store, and the contract must not leak sheet mechanics.

**Considered Options**: prod smoke read-only, write path smoked in staging only (rejected — leaves the prod write path unsmoked forever, failing the smoke's stated purpose); real-tab write + general delete endpoint (rejected — destructive surface on real data, junk window on crashed runs); "last non-empty row" delete inference (rejected — non-deterministic); dedicated smoke route instead of header (rejected as unnecessary — the header keeps one contract and the scope is orthogonal to the route).

**Consequences**: the deployed suite gains match + category read assertions against the real tabs (read-only — those tabs' read anchors get smoked, their write anchors never do); real-tab write anchors are verified only by first real use, accepted because ranges are static deployed config; `Smoke Test` tabs are permanent, visible artifacts of every environment's spreadsheet; the whole smoke-scope mechanism is a Sheets-era device that dies with the Postgres migration (there, delete becomes an ordinary `DELETE /expense/{id}` over a real PK).
